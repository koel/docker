koel/docker
===========

[![docker-pulls-badge]][docker-hub] ![Continuous testing and deployment](https://github.com/koel/docker/workflows/Continuous%20testing%20and%20deployment/badge.svg)

A Docker image with only the bare essentials needed to run [Koel]. It includes Apache and a PHP runtime with required extensions.

> [!NOTE]
> Instructions on `master` may not match the version you're running.
> For version-specific documentation, switch to the corresponding tag (e.g., [`v8.3.1`](https://github.com/koel/docker/tree/v8.3.1)).

> [!IMPORTANT]
> This image does not include a database. A separate database container (MariaDB/MySQL or PostgreSQL) is required.
> Ready-to-use Docker Compose configurations are provided — see [Quick Start](#quick-start).

## Quick Start

[Docker Compose][docker-compose] is the easiest way to get started. Clone this repository, pick a compose file for your preferred database, fill in the passwords and the Reverb keys (see [Background jobs and live updates](#background-jobs-and-live-updates)), and run:

```bash
# For MariaDB/MySQL
docker compose -f docker-compose.mysql.yml up -d

# For PostgreSQL
docker compose -f docker-compose.postgres.yml up -d
```

## Initial Setup

### The `koel:init` command

This command handles migrations, generates the `APP_KEY`, creates the default admin account, and performs other first-run tasks. It runs automatically when the container starts (disable with `SKIP_INIT=true`), but you can also run it manually:

```bash
docker exec --user www-data -it <koel_container> php artisan koel:init --no-assets
```

The `--no-assets` flag skips building front-end assets, as they are already included in the image.

### Default admin account

The first `koel:init` creates a default admin account:

* **Email:** `admin@koel.dev`
* **Password:** `KoelIsCool`

**Change this password immediately:**

```bash
docker exec -it <koel_container> php artisan koel:admin:change-password
```

You can also update the email and password via the web interface after logging in.

## Configuration

### Preserving `APP_KEY`

`APP_KEY` is generated during `koel:init` and is essential for encryption. If the container is recreated without persisting this key, you'll need to re-initialize. Two ways to preserve it:

**Option 1: Bind-mount the `.env` file**

```bash
touch .env
docker run -d --name koel \
    -p 80:80 \
    --mount type=bind,source="$(pwd)"/.env,target=/var/www/html/.env \
    phanan/koel
```

**Option 2: Pass `APP_KEY` as an environment variable**

```bash
# Generate a key
docker run -it --rm phanan/koel php artisan key:generate --show

# Pass it to your container
docker run -d --name koel \
    -p 80:80 \
    -e APP_KEY=<your_app_key> \
    phanan/koel
```

### Environment variables

> [!IMPORTANT]
> This list is not exhaustive. See [`.env.example`][koel-env-example] for a complete reference.

| Variable | Description |
|---|---|
| `SKIP_INIT` | If set, prevents the container from running `koel:init` on startup. |
| `DB_CONNECTION` | `mysql`, `pgsql`, `sqlsrv`, or `sqlite-persistent`. |
| `DB_HOST` | Hostname of the database container. Must be on the same Docker network. |
| `DB_USERNAME` | Database username (default: `koel`). |
| `DB_PASSWORD` | Database password. Must match the database container's configuration. |
| `DB_DATABASE` | Database name (default: `koel`). |
| `APP_KEY` | Base64-encoded key generated by `koel:init` or `key:generate`. |
| `FORCE_HTTPS` | Set to `true` if using an HTTPS reverse proxy in front of Koel. |
| `MEMORY_LIMIT` | Memory limit in MB for the scanning process. |
| `LASTFM_API_KEY`, `LASTFM_API_SECRET` | Enables [Last.fm integration](https://docs.koel.dev/3rd-party.html#last-fm). |
| `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET` | Enables [Spotify integration](https://docs.koel.dev/3rd-party.html#spotify). |
| `OPTIMIZE_CONFIG` | Preloads and optimizes configuration. Changes require a container restart. |
| `QUEUE_CONNECTION`, `REDIS_HOST` | Run background jobs through a queue, e.g. `redis` and the Redis container's hostname. See [Background jobs and live updates](#background-jobs-and-live-updates). |
| `BROADCAST_CONNECTION`, `REVERB_*` | Enable live updates and the remote controller with Reverb. See [Background jobs and live updates](#background-jobs-and-live-updates). |

### Background jobs and live updates

The compose files run two extra containers from the same image next to Koel:

* `queue` (`command: queue`) works through background jobs, which Koel puts on Redis with `QUEUE_CONNECTION=redis`.
* `reverb` (`command: reverb`) runs [Reverb](https://reverb.laravel.com), which powers live updates and the [remote controller](https://docs.koel.dev/usage/remote-controller). Koel's container forwards `/app/` and `/apps/` to `reverb:8080`, so browsers reach Reverb on Koel's own address. This container must be named `reverb` and be on the same network as Koel.

If you set these containers up yourself, give `queue` and `reverb` the stop signal `SIGTERM` (`stop_signal: SIGTERM` in compose). The image's default stop signal is for Apache, so they would only stop when Docker kills them.

Both need the same configuration as Koel. The compose files share it through the `x-koel` block, so put your settings there, including `APP_KEY` (see [Preserving `APP_KEY`](#preserving-app_key)). If you mount a `.env` file instead, mount it into all three containers.

Koel and `queue` also share the `artifacts` volume through `ARTIFACTS_PATH`, because jobs pick up files that Koel saved, such as uploads. The `queue` container sends live updates straight to `reverb`, so it sets its own `REVERB_HOST`, `REVERB_PORT` and `REVERB_SCHEME`.

For Reverb, fill in `REVERB_APP_KEY` and `REVERB_APP_SECRET` with random strings, and set `REVERB_HOST`, `REVERB_PORT` and `REVERB_SCHEME` to the address you open Koel at, e.g. `koel.example.com`, `443` and `https` behind an HTTPS reverse proxy. The reverse proxy must pass WebSocket connections on. Caddy and Traefik do this on their own. For nginx, add this to the `location` block that proxies Koel:

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
```

You can run `queue` without Reverb, but Reverb needs `queue`: with live updates on, Koel hands uploads and other jobs to the queue. To use neither, leave out the `queue`, `reverb` and `redis` services, the `artifacts` volume and their settings, and Koel runs jobs right away as before.

## Managing Music

Koel's init script installs a [scheduler](https://docs.koel.dev/cli-commands#command-scheduling) that scans `/music` daily. To trigger a manual scan:

```bash
docker exec --user www-data <koel_container> php artisan koel:sync
```

## Volumes

| Path | Description |
|---|---|
| `/music` | Your music library. |
| `/var/www/html/storage/app/public/images` | Uploaded images (album art, user avatars, etc.). |
| `/var/www/html/storage/search-indexes` | Search indexes for songs, albums, and artists. |
| `/var/www/html/storage/app/artifacts` | Uploads in progress, transcodes and other files that Koel and the `queue` container share. Used when `ARTIFACTS_PATH` points here, as in the compose files. |

## Ports

Only port **80** (HTTP) is exposed. Set up a reverse proxy for HTTPS support.

## Workdir

The container's working directory is `/var/www/html` (Apache's document root). All Koel files reside here.

## Local Development

The `Makefile` contains several helper commands for local development. For example, to build and start the dev stack:

```bash
make start
```
